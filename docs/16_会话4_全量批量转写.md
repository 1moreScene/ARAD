## 1. 方法论（本会话确立的"两层还原"体系）

```
L1 精修层（人工语义还原）   130 函数
   src/nengine/* (time_system/camera_fx/net_socket)
   src/cnrd/* (CNRDObject/Collision/Active/Equipment)
   src/game/module/CNMainGameModule.cpp
   → 每个函数：语义命名 + 结构注释 + 研究文档交叉引用 + 逐行人工转写
   → 对应文档 docs/10-15

L2 转写层（脚本规范化转写） 9,451 函数
   src/game/* + src/combat/* + src/nengine/{log_dump,gfx_texture} 等 21 个大模块文件
   → 反编译输出的规范化重排：类型名清洗（Hex-Rays 风格 → 标准 C++）、
     VA 标记、按 64K 区块分模块、统一头注释
   → 语义与 IDA Hex-Rays 输出逐字对应（无信息损失、无臆造）
   → 后续"逐模块精修"的工作队列（从 L2 提升到 L1）
```

**为什么要两层**：12,172 函数的体量下，一次性追求全量 L1 不现实。
L2 先把**全部反编译产物固化为可读源码树**（也让 VA 索引可 grep 全库），
L1 再按价值排序逐个模块精修——这是可持续的工程化路径。

## 2. 批量反编译工程（tools/idar_bulk_dump2.py）

- 多分区链式批处理：`DUMP_PARTS=xxx` 环境变量驱动，单次 IDA 会话跑多区块
- 函数大小过滤：>8KB 巨型函数跳过并记录（避免 Hex-Rays 卡死；现存 SKIPPED-BIG 清单）
- 防死循环修复：`ea = max(f.end_ea, ea+16)`
- 防丢盘：每 200 函数写盘一次
- 并行化：4 份 i64 副本 + 4 个 IDA 进程（**教训**：kill IDA 后 i64 可能残留
  `.id0` 锁文件导致后续会话 error 4——恢复方法 = 全删 ARAD_*.* 从母本重拷）

## 3. 转写引擎（tools/transcribe.py）

- 解析 dump → 按 PLAN 表分派到 21 个模块文件（区块 → 文件映射见脚本）
- 类型清洗表：`unsigned __int16`→`uint16_t` 等 20 条规则（**长模式优先**的排序教训：
  首版因 `__int16` 先替换导致 `unsigned int16_t` 残形，已修复并全量重跑验证清零）
- 每函数 `// 0xXXXXXX 名称` 标记（可 grep 全库 VA 索引）
- 文件头：来源 dump + 区块 + 层级声明 + 函数计数
