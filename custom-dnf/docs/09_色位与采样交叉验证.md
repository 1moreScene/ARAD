# 色位与采样交叉验证

用户反馈重制精灵更像马赛克，并启动原版允许交叉验证、关闭进程。本轮发现两个真实差异，已修正：IMG的5位颜色展开，以及精灵变换/桌面125%显示的采样。

## 原版当前真实参数

只读`ARAD.exe`渲染对象，不向原版注入代码或改写状态：

| 项目 | 实测 |
|---|---|
| 游戏启动请求 | 640×480，depth16 |
| 当前窗口后缓冲 | 640×480，D3DFMT_X8R8G8B8=22，实际32位 |
| DPI awareness | 0，不感知DPI |
| 当前桌面显示 | 120DPI/125%，800×600 |
| Sprite Begin指针 | 0x67F1C6 |
| 该入口PE设置 | stage0 MAGFILTER16=2，MINFILTER17=2，MIPFILTER18=0 |

纹理过滤2是LINEAR，MIP0不使用mipmap。原版静态D3DXSprite入口`67F42E/67F43F`调用D3D8设备vt+252设置两项过滤。底层素材本身仍使用16位A1R5G5B5/A4R4G4B4等格式，**素材位深、启动请求和窗口实际后缓冲是三个不同信息**。

线性采样的通用定义可对照[微软官方说明](https://learn.microsoft.com/en-us/windows/win32/direct3d9/linear-texture-filtering)；本客户端的具体常量与入口以本地D3D8 PE为证，不以D3D9默认值推定原版行为。

## 颜色逐像素对照

同一原版窗口采集逻辑客户区DC；对照资源StatusWindow[0]在(29,63)的静态不透明边框/底纹，排除人物插画和动态文字，共14367像素。

| 5位→8位展开 | RGB通道平均绝对误差 |
|---|---:|
| 旧算法`n<<3` | 1.77685 |
| `round(n*255/31)` | 0.17893 |
| 实测相符`(n<<3)|(n>>2)` | **0** |

旧算法最大颜色248，漏掉低位补齐。当前IMG解析器使用实测相符的位复制，最大255；0x0F则每通道4位复制为8位，保留半透明alpha。这个修正改善颜色，但颜色位扩展不是非整数放大粗糙感的主要原因。

## 显示取样对照

原版逻辑DC640×480和桌面物理800×600一起采集；原版当时部分被Codex遮挡，因此只比对未遮挡的静态面板ROI(36,84,328,548)，不把遮挡区域计入误差。

| 将逻辑DC放大后的方法 | 相对原版桌面画面MAE |
|---|---:|
| 最近邻 | 12.40565 |
| 双线性 | **0.75359** |
| 三次 | 4.44303 |

据此原版的系统放大更接近双线性。重制以前GDI COLORONCOLOR与变换精灵的最近邻取样，会在125%倍率上把同一源像素复制成不均匀宽度；用户描述的颗粒/锯齿与这个差异一致。

## 修正和验证

窗口使用预计算并复用的双线性采样计划，把640×480画布转换为物理尺寸，再GDI按1:1复制；不会让GDI重复放大。缩放/旋转精灵改线性取样，整数1:1/镜像仍直接复制以保留原始像素与锚点。

`--scale 1`的输出与逻辑画布逐像素一致；默认800×600原生输出相对双线性参考MAE0.16066，相对最近邻10.75692。`tools/verify_custom_rendering.py`验证了真实窗口，并生成`out/rendering-verified/sampling-comparison.png`。对照左右使用同一源图/同一物理大小，左为最近邻参考、右为实际修正后截图，再等倍放大局部便于看差异。

证据：`tools/inspect_rendering.py`、`work/rendering_evidence/report.json`、原版逻辑/物理截图及PE片段。原版正常关闭请求未生效；按用户已给的授权核对绝对路径后结束该ARAD进程，未触碰服务器或其他进程。

当前130项测试、clippy/fmt通过；UI、受击、音效与窗口策略回归另见相应报告。动态中文字体、D3D8浮点取样/舍入、驱动和其他DPI比例未全部逐像素复刻，不能把上述静态颜色一致扩展成整帧渲染完全一致。
